# Worktree-per-issue orchestration

Several GitHub issues are driven in parallel — one git worktree + dev server
per issue. This is the policy an agent (or person) follows to dispatch and
land that work. The driving agent **orchestrates and does not implement**: it
cuts issues, fans out one subagent per issue, monitors, and garbage-collects —
it does not write the code itself.

Written against `gominimal/webapp`; paths and port ranges below are that
repo's conventions (documented in its `local-dev-setup` skill).

## Intake

The automation operates as GitHub user **`agent-137`**. Issues assigned to it
are its queue:

```sh
gh issue list --assignee agent-137 --state open
```

When cutting a new issue, use a **plain body + a `kind:*` label**
(`kind:feature` / `kind:bug` / `kind:chore`) — no SDD/spec templates or
`sdd:*` labels (that's a separate experimental automation). Assign `agent-137`
and set **`mitodrummer`** as the PR reviewer.

## Fan out — one subagent per issue, in parallel

For each issue, spawn **one background subagent** that owns a worktree
end-to-end. When there are several issues, fan them **all out at once** — the
per-worktree dev servers let the parallel agents' local convergence (and
the single post-push CI wait) overlap instead of serializing. Each subagent's
lifecycle:

1. **Create the worktree under `webapp/.worktrees/webapp-<issue>`**, branched
   off `main` — **always** under `.worktrees/`, never `/tmp` (it's wiped on
   sandbox exit, and a cross-device `git worktree move` out of `/tmp` fails
   with "Invalid cross-device link"; `webapp/` is the only writable+persistent
   tree). The `.worktrees/` gitignore + the Vite `server.watch.ignored`
   entry keep nested worktrees out of `git status` and out of HMR.

   ```sh
   git -C <repo-root> worktree add .worktrees/webapp-<issue> -b <branch> main
   ```

2. **Full setup**, or the dev server 500s: `pnpm install --frozen-lockfile`,
   then copy the two gitignored inputs from the main checkout —
   `.env.local` and `src/content/packages/` (missing either is the usual 500
   cause):

   ```sh
   cp <repo-root>/.env.local .env.local
   cp -r <repo-root>/src/content/packages src/content/
   ```

   Copying is the only in-sandbox path for `src/content/packages/`: it is
   generated by `minimal dump --packages | node scripts/generate-package-data.ts`,
   and the `minimal` CLI works host-side only (not available in the sandbox —
   tracked in gominimal/minimal#601).

   `.env.schema` is committed, so it comes with the checkout — only `.env.local`
   needs copying. The dev server loads env through `varlock run --` (validates
   `.env.local` against the schema), so a worktree whose copied `.env.local` is
   missing a `@required` var fails to boot with a message naming it, rather
   than 500ing at request time. Run `pnpm env:check` to validate before starting.

   The copied `.env.local` already points `VULNDB_DATABASE_URL` at the shared
   `:5433` proxy — do **not** start a per-worktree proxy; the boot-started
   shared one already serves every worktree.
3. **Start a dev server on a unique port** in the `4322..4350` range
   (`scripts/dev.sh --port <N> start`). Worktrees start at **4322**: `:4320`
   is reserved for the discovery dashboard (tailnet-dashboard loadout) and
   `:4321` is your own (non-worktree) main dev server. Honor the repo's
   discovery contract — a server only counts as up if `GET /healthcheck`
   answers 200 on the recorded port (`strictPort` makes a port collision fail
   loudly instead of silently walking to another port). The dashboard's
   reconciler tailnet-serves each healthy port within ~10s of it appearing.
4. **Do the work.** Commit freely on the branch — local commits are free; it's
   *pushes* that cost Actions minutes.
5. **Converge locally before the first push — this is the primary
   Actions-budget lever.** Every push re-runs the whole Actions suite (Type
   Check & Lint, Unit, E2E, Build, runtime-image materialize) **and** both
   review bots (claude-review + CodeRabbit), so push-per-iteration is by far the
   dominant spend. Do all iteration in-sandbox first, where it costs zero
   Actions:
   - **Mirror CI locally until clean:** `pnpm check && pnpm lint && pnpm test &&
     pnpm build`. Add `E2E_PORT=<free port in 4322–4350> pnpm e2e` for any
     user-facing change (E2E is required for new pages/interactions; without
     `E2E_PORT`, Playwright's `reuseExistingServer` may silently test whichever
     worktree holds the default :4322). Fix until all pass.
   - **Run the local review loop to convergence:** use the **`review-fix-loop`**
     skill — it reviews the same `origin/main...HEAD` diff the cloud
     claude-review sees and fixes findings, so "local loop reports no findings"
     strongly predicts a clean cloud review. Its default is 3 cycles; if it's
     still surfacing issues, raise the cap (e.g. "run 5 loops") and keep going
     **until it reports clean** — don't push a loop that's still finding things.
     Run `/security-review` locally too for anything touching auth, middleware,
     or secrets.
6. **Push once, then open the PR** (base `main`, reviewer `mitodrummer`; plain
   factual description, only what's in the diff). Local fix commits accumulate
   and push together — do **not** push after each fix.
7. **`/shipit` to verify, not to iterate.** CI and both bots still run on the
   push (intended — that's the authoritative gate), but because you converged
   locally they should pass first try. Address any genuinely new cloud-only
   finding (claude-review Must-fix + Should-fix, CodeRabbit Critical + Major),
   but expect none — every re-push is another full Actions run plus two more bot
   reviews, so treat a second push as a real cost, not a reflex. When
   CodeRabbit's `CHANGES_REQUESTED` stays pinned to a superseded commit after
   its findings are fixed: first resolve every unresolved thread, then comment
   `@coderabbitai full review` on the PR to trigger a fresh pass on the current
   head — that flips the state. If its latest pass on the head is already clean
   (0 unresolved threads) and only the old verdict lingers, dismiss the stale
   review so it doesn't falsely block the merge:

   ```sh
   gh api -X PUT repos/{owner}/{repo}/pulls/<n>/reviews/<id>/dismissals \
     -f event=DISMISS -f message="stale: superseded commit; findings fixed"
   ```

## Merge gate (do NOT cross)

The subagent stops at **green + reviews-addressed**. It does **not** merge and
does **not** arm GitHub auto-merge (auto-merge would land the instant checks
pass, possibly before claude-review posts). **`mitodrummer` reviews and
merges.** Never comment a literal `/shipit` on the PR — "shipit" means running
the shipit skill locally.

## Cleanup (after a PR merges)

Garbage-collect the worktree so `git status` stays clean (and the discovery
dashboard drops the dead server).

> **Run only after the PR has merged.** `git worktree remove --force` discards
> any uncommitted/unpushed changes in the worktree and `git branch -D` deletes
> the branch unconditionally (not the merge-checked `-d`) — both are
> unrecoverable. Confirm the PR is merged and nothing local is unpushed first.

```sh
( cd .worktrees/webapp-<issue> && scripts/dev.sh --port <N> stop )
git worktree remove .worktrees/webapp-<issue> --force
git branch -D <branch>
git worktree prune
rm -f "${TMPDIR:-/tmp}/minimal-dev-<N>.pid"
```

## Status

Status is **pull-based** — don't push unsolicited per-completion progress
boards. Surface only genuine blockers or decisions that need a human
(e.g. a missing secret, a product call, CI/review infra down).
